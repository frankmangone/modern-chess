# Accounts with Clerk, built to be replaced

Roadmap step 2. Users need an owner for what they create, and guest tokens last seven days.
Clerk is the first sign-in provider because its free tier is enough (50,000 monthly retained
users, email and Google sign-in, no card). The design keeps Clerk at the edge, so changing
provider later is a configuration change plus a one-off data step, not a rewrite.

## The rule that keeps us portable

**Only social-api ever sees a provider token, and only once.** Everything else keeps using our
own Ed25519 token and our own `users.id`.

- game-api does not change. It verifies our tokens offline, as today.
- Matches, lobbies and (later) games and communities are owned by `users.id`, never by a
  provider id. A provider id exists in one table and nowhere else.
- The web app talks to a small `AuthProvider` interface. Clerk is one implementation.
- social-api verifies provider tokens with a generic OIDC/JWKS verifier configured by
  environment variables (issuer, JWKS URL, optional allowed origins). Clerk, Auth0, Logto,
  Cognito and most others fit it. Changing provider means new values, not new code.
- The backend holds no provider secret. Verification uses public keys only. The only value
  the web app needs is Clerk's publishable key, which is public by design.

## Flow

1. The visitor plays as a guest as today (`POST /api/social/guests`).
2. They choose "Sign in". The web app opens Clerk's sign-in and gets a Clerk session token.
3. It calls `POST /api/social/session` with that token as the bearer credential, and the
   current guest token in the body when there is one.
4. social-api verifies the provider token, then decides:
   - **The identity is already linked to a user:** sign in as that user. The guest's matches
     stay with the guest (merging across the two databases is a later step).
   - **Not linked, and the guest token is valid and the guest has no identity yet:** link the
     identity to the guest's existing user row. The account adopts the guest, so the matches
     are kept and no data moves.
   - **Not linked, no guest:** create a user with a generated handle and link it.
5. It answers with our token and user, the same shape as `/guests`. The web app stores it in
   place of the guest token.
6. When our token expires and the Clerk session is still alive, the web app repeats step 3
   without asking the person to sign in again. Guests who never sign in behave as today.

## Data

New migration in `crates/social/migrations`:

```
identities (
  provider    TEXT        NOT NULL,   -- the configured provider's label, e.g. "clerk"
  subject     TEXT        NOT NULL,   -- the provider's user id (Clerk: "user_...")
  user_id     UUID        NOT NULL REFERENCES users (id),
  email       TEXT,                   -- verified email when the token carries it
  created_at  TIMESTAMPTZ NOT NULL,
  PRIMARY KEY (provider, subject),
  UNIQUE (user_id, provider)
)
```

`users` gains a nullable `deleted_at`. The email is stored so a future provider can be matched to existing
users at their first sign-in (verified email equals stored email), which is the migration
path. It is never logged and never returned by any endpoint.

Migration to another provider, when the time comes: export users from Clerk (included in
the free plan), point the verifier at the new issuer, and on first sign-in link by verified
email to the existing user. Old subjects stay in the table until the old provider is gone.

## Slices (each its own branch and PR)

1. **Backend accounts** (`feature/accounts-backend`, done). Settings: `SOCIAL_PROVIDER_NAME`,
   `SOCIAL_PROVIDER_ISSUER`, `SOCIAL_PROVIDER_JWKS_URL`, `SOCIAL_PROVIDER_AUTHORIZED_PARTIES`. `identities` table and repo; a
   `ProviderVerifier` (RS256 via JWKS, cached, refetched once on an unknown key id; checks
   `iss`, `exp`, `nbf`, and `azp` when configured); `POST /session`; `DELETE /me`
   (removes identities and the email, renames the handle to `deleted-<hex>`, marks the user
   deleted so its leftover token stops working, keeps the row so finished matches still resolve). Tests run against a locally generated RSA
   key and a fake JWKS, so no Clerk account is needed.
2. **Rate limiting** (`feature/rate-limits`). Per-client limits on both APIs, tighter on
   `/guests` and `/session`. Behind the tunnel the client address comes from a header, so the
   trusted-proxy setting is explicit and off by default.
3. **Web sign-in** (`feature/accounts-web`). `AuthProvider` interface, Clerk implementation
   using `@clerk/clerk-js` loaded on demand (no dependency on the community Solid wrapper),
   Sign in / Sign out and the handle in the header, silent re-exchange, a delete-account
   button that calls our endpoint and then Clerk. Guests keep working without any of it.
4. **Docs and the tunnel**. README setup for the Clerk keys, `make share` notes, roadmap.

## Decisions I made (change any of these)

- Email and Google sign-in, nothing else. Passkeys and MFA are paid on Clerk and not needed.
- Handles: an adopted guest keeps `Guest-1234`; a new account gets a generated one. Choosing
  a handle is a later, separate change.
- Store the verified email, as above. If you would rather store nothing, migration then
  needs a one-off script mapping old ids to new ones.
- `azp` (the origin that asked for the token) is checked only when
  `SOCIAL_PROVIDER_AUTHORIZED_PARTIES` is set, and a token with no `azp` passes (the
  provider's own documentation says to skip the check then). The token travels in a header,
  not a cookie, so the risk the check guards against is small. A wildcard on a free tunnel
  domain would allow every tunnel anyone can open, so for `make share` the list stays empty.
- Provider keys are trusted for an hour, then fetched again, so a key the provider withdraws
  stops working. If the provider cannot be reached, the old copy keeps working.

## Known limits (accepted for now)

- Tokens cannot be revoked. A guest token is proof of being that guest for up to 7 days, so a
  stolen guest token could be used to adopt that guest into someone else's account, and a
  leftover pre-sign-in guest token can still call `DELETE /me` on the adopted account until it
  expires. Closing this means short-lived tokens or a revocation list, or asking for a fresh
  provider token to delete. Not done in this slice.
- game-api checks tokens offline, so a deleted account's token keeps working there until it
  expires. Handles are generated today, so no personal data stays behind; when users can
  choose handles, deleting must also clear them where the game side stored them.
