# Roadmap after the first playable app

Where the hub goes from here, in the order we expect to work on it. Sizes are rough: **S** is a
day or less, **M** a few days, **L** a week or more. Each step is its own branch and PR.

The goal behind all of it: users propose games, and communities form around them with mods,
drills, puzzles and skins. Admins only make a few common games.

## Done and in review

- Picture skins for all six games (#41, merged).
- Match page laid out as designed, with captured pieces and material from the server (#42).

## 1. Board skins and Xiangqi (this branch) [M]

Boards where pieces sit on line crossings instead of squares, so Xiangqi and later Go can be drawn.

- Skin option `board`: `intersections` style, background and line colours, `breaks` (the river),
  `diagonals` (palaces), `dots` and `crosses` (star points), `labels` (river text).
- Skin options `colours` (a colour per player) and `pieceStyle: "disc"` for round pieces.
- A Xiangqi catalogue page with piece values for the material count.
- Not included: a cover picture. It needs an image from the project's own set.

## 2. Accounts with Clerk [M]

The design and slices are in `2026-11-10-accounts.md`. Clerk does the sign-in screens and
Google sign-in, and the backend is built so the provider can be replaced later.

Everything users create needs an owner, and guest tokens last seven days.

- social-api: verifies the provider's token and answers with our own Ed25519 token, so
  game-api does not change.
- A guest who signs in keeps their matches.
- Guests stay able to play.
- Rate limiting, at the gateway rather than in the apps (`deploy/nginx.conf`, done for `make share`). A real deployment puts the same limits at its own edge, for instance Cloudflare's.
- Account deletion, and email addresses never in logs.
- **Needs from Frank:** a Clerk development instance (email code and Google on); its publishable key and Frontend API URL.

## 3. Go [L]

The board skin from step 1 covers how it looks. The engine needs four things, each one a general
switch in the spec rather than something Go-shaped:

- Placing a stone from an unlimited supply (`unlimited_supply` on a piece).
- Capturing groups that have no liberties, and refusing suicide (`liberty_capture`), with ko as
  `forbid_repeated_positions`.
- A pass command through the engine, session, API, wasm and the page (`allow_pass`).
- Scoring: area scoring as a new win condition (`AREA_SCORE`).
- Boards of 9x9, 13x13 and 19x19.

Done in two pull requests: the engine, session, server, wasm and docs (#45), then the web app,
the three Go boards (9x9, 13x13, 19x19) and a playable board in the book. Still open: a
cover picture for Go, and agreeing dead stones before the count.

### Games and variants

Go started as three catalogue pages. It is now one game with three variants: a game is a
container (page text, cover, how to play, "Try it") and its variants are what people play.
Variant slugs are the slugs of the rules, so matches and lobbies did not change. The design is in
`2026-11-10-games-and-variants` (spec and plan). The server half is built; the web half (the
variant picker, labelled lobbies, the match title) is the next pull request, and the two merge
back to back. This is also where community variants will land: a user's variant is a new
variant under an existing game.

## 4. Play against the computer [M]

A game-agnostic search bot (Monte Carlo tree search) that runs in a web worker against the wasm
engine, so it works for every game including ones users add. Difficulty levels, and a practice
page as in the design. Stockfish in wasm for chess only can come later.

## 5. Community content, in slices [L overall]

In this order, because each slice makes the next one safer:

1. **Skins:** image files only. Inline SVG skins are trusted today and must not be accepted from users.
2. **Puzzles and drills:** a saved position plus a solution, checked by the engine, with progress per user.
3. **Variants:** a forked spec, with limits on board size and pieces, a time budget per move, and a review step.
4. **Community pages:** owners, mods, game proposals, reporting, and spec versions so running matches survive a rule change.

The engine's rule vocabulary is the real limit here. Go will show how often a good idea needs a new rule type.
